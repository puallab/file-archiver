# file-archiver 요구사항

2026-10-17 · dohyun

## 개요

file-archiver는 설비가 만든 검사 파일을 모아 박스·출하 단위로 압축하고, 출하 시점에 모든 제품의 검사 데이터를 하나의 파일로 내려받게 하는 시스템이다.

**배경.** 회사에서 설비 약 70대가 초당 2\~3건씩 수십 KB짜리 검사 파일을 올리고, 출하 한 건에 10만\~40만 건을 압축해야 했다. 기존 구현은 진행률·완료 여부를 알 수 없었고, 실패·재시도·동시 요청을 고려하지 않았다.

**목표.** 같은 문제를 처음부터 다시 설계해, 파일 수가 늘거나 저장소가 바뀌어도 안정적으로 동작하게 만든다. 그 과정에서 각 기술 선택의 트레이드오프를 직접 검증한다.

**범위.**

- 포함: file-agent(검사 파일 수집·업로드·등록), 박스 포장과 박스 압축, 출하와 출하 압축, 출하 단위 다운로드, 진행률 조회
- 제외(이번 버전): 파우치 단위, 백업 서버 전송, 완료 알림, 재시도 정책, 인증·권한, MES 업무 정보(작업자, 제품코드, 고객사, 출하 요청·확정 흐름, 채번 규칙, 취소 이력)

**용어.**

| 용어 | 뜻 |
| --- | --- |
| 검사 파일 | 마지막 공정 설비가 만든 .txt 파일. 파일명이 제품 시리얼이다 |
| 시리얼 | 제품 하나의 식별자 |
| sensorId | 첫 공정에서 정해지는 값. 참고용으로 저장한다 |
| 박스 | 시리얼 여러 개를 묶은 포장 단위(packaging). 실물 박스(BOX)는 포장 시 1차 압축한다. 출하 때 박스 없는 낱개 시리얼은 가상 포장(VIRTUAL) 하나로 묶고 미리 압축하지 않는다 |
| 출하 | 박스와 낱개 시리얼을 묶은 최종 단위. 하나의 zip으로 압축한다 |
| Job | 박스 압축이나 출하 압축처럼 비동기로 처리되는 작업 단위 |

## 기능 요구사항

수집은 사실만 기록하고, 어떤 파일을 쓸지는 포장·출하 시점에 서버가 정해 파일 ID로 고정한다.

**수집 (file-agent)**

| ID | 요구사항 |
| --- | --- |
| FR-1 | agent는 지정 폴더의 .txt 파일을 감지해 스토리지에 업로드한다 |
| FR-2 | agent는 업로드한 모든 파일을 서버에 등록한다 (시리얼, 검사 시각, sensorId, 업로드 설비, 스토리지 key). 유효성은 판단하지 않는다 |
| FR-3 | 시리얼은 제품당 유일하다. 검사 파일은 파일 ID(대리키)로 저장하고, 시리얼+검사 시각이 같은 등록은 한 번만 저장한다 |
| FR-4 | 스토리지 원본은 출하 완료일 기준 60일 뒤 삭제한다. 설비 로컬 파일은 관리하지 않는다 |

**박스 포장**

| ID | 요구사항 |
| --- | --- |
| FR-5 | 박스 포장 요청은 시리얼 목록을 받는다. 박스 ID는 archiver가 대리키로 발급한다 |
| FR-6 | 시리얼 중 하나라도 검사 파일이 없으면 포장 전체를 거절한다 |
| FR-7 | 이미 다른 박스에 포장된 시리얼이 있으면 포장 전체를 거절한다. 거절 시 어떤 시리얼이 어떤 사유로 거절됐는지 응답한다 |
| FR-8 | 포장 시 각 시리얼의 최신 검사 파일을 박스에 고정하고, 압축은 포장과 분리해 비동기 Job으로 처리한다. 박스 상태는 대기(PENDING), 압축 중(PROCESSING), 완료(PACKED), 실패(FAILED)를 갖는다. 출하도 대기(PENDING), 압축 중(PROCESSING), 완료(COMPLETED), 실패(FAILED)를 같은 의미로 쓴다 |
| FR-9 | 박스 포장 취소는 압축이 끝난 출하 전 박스에만 가능하다. 출하 취소·반품 이후에는 다시 가능하다. 취소하면 박스와 박스 zip을 삭제하고 시리얼은 검사 완료 상태로 되돌린다 |

**출하**

| ID | 요구사항 |
| --- | --- |
| FR-10 | 출하 요청은 박스 목록과 박스에 안 담긴 시리얼을 함께 받을 수 있다. 낱개 시리얼은 박스 포장과 같은 검사를 거친 뒤 출하마다 가상 포장 하나로 묶는다. 출하 ID는 archiver가 대리키로 발급한다 |
| FR-11 | 압축이 끝나지 않은 박스나 이미 출하된 박스가 있으면 출하 전체를 거절한다 |
| FR-12 | 출하 최종 파일은 모든 검사 파일을 풀어서 하나의 zip으로 합친다. 박스는 박스 zip 항목을 그대로 복사(raw copy)하고, 가상 포장은 고정된 원본 파일을 읽어 넣는다 |
| FR-13 | 출하 취소 시 출하와 최종 zip을 삭제하고, 포함된 박스는 출하 전 상태로 되돌리고, 가상 포장은 삭제해 낱개 시리얼을 검사 완료 상태로 되돌린다 |

**다운로드**

| ID | 요구사항 |
| --- | --- |
| FR-14 | 다운로드는 출하 단위로만 제공하며, 최종 압축이 끝난 출하만 받을 수 있다 |
| FR-15 | 다운로드는 웹에서 presigned URL로 제공한다 |
| FR-16 | 출하 압축 진행률은 폴링으로 조회하며, 완료된 포장 단위 / 전체 포장 단위로 계산한다. 박스 1개와 가상 포장 1개를 각각 1단위로 센다 |

## 비기능 요구사항

기준은 설비 70대, 출하 최대 40만 건이고, 100만 건까지 버티는 것을 목표로 한다.

| ID | 요구사항 | 기준값 |
| --- | --- | --- |
| NFR-1 | file-archiver의 장애나 지연이 설비 동작에 영향을 주면 안 된다 | 서버가 멈춰도 agent는 계속 동작하고, 밀린 파일은 복구 후 이어서 보낸다 |
| NFR-2 | 포장 트랜잭션은 짧게 끝나며, 압축이 포장 응답을 지연시키지 않는다 | 포장 트랜잭션 안에서 스토리지 작업 없음 |
| NFR-3 | 검사 파일 등록을 지속 처리한다 | 초당 210건 이상 |
| NFR-4 | 대규모 출하를 안정적으로 처리한다 | 출하당 최대 40만 건, 목표 100만 건 |
| NFR-5 | 박스 압축 시간 | 수백 건 기준 10초 이내 |
| NFR-6 | 출하 압축 시간 | 목표 5분, 최대 10분 |
| NFR-7 | 압축 도중 장애가 나면 해당 Job을 처음부터 다시 수행할 수 있다 | 부분 산출물은 정리하고, 실패한 압축은 최대 3회까지 다시 시도한다 |
| NFR-8 | 처리 용량을 넘는 포장·출하 요청이 몰려도 서버는 죽지 않는다 | 넘친 요청은 거절하지 않고 대기(PENDING)로 DB에 남겨 차례로 처리한다 |

참고로 40만 건을 5분에 처리하려면 초당 약 1,300개 파일을 처리해야 한다. 100만 건이면 최종 zip이 수십 GB라 나눠 올리기(멀티파트 업로드)가 필요하다.

| 2026-10-17 | 서버 코드는 file 처리, inspection\_file, shipment·packaging·product, 작업 실행의 네 덩어리로 나눈다 (도메인 결정 문서) | 문제 1\~6을 고칠 때 열어야 하는 곳이 가장 적다. 한 트랜잭션에서 같이 바뀌는 테이블은 한 덩어리로, 포장·출하에 똑같이 쓰이는 재처리는 한 곳에 둔다 | 행위별 세분화(포장·출하·제품 각각 분리) |
| 2026-10-15 | 몰린 포장·출하 요청은 거절하지 않고 PENDING(대기)으로 저장한다. 압축 중 상태는 PROCESSING으로 이름을 바꾼다 | 대기 요청이 DB에 남아 서버가 죽어도 사라지지 않고, 재시작 후 다시 집어 갈 수 있다 | 넘친 요청 거절(429·503), 메모리 대기열 |
| 2026-10-11 | product 테이블(PK 시리얼)은 제품당 1행이다. 첫 검사 등록 때 만들고, 상태는 INSPECTED → PACKED 하나로 둔다 | 1행 조건부 UPDATE로 FR-7을 막을 수 있고, 박스 취소가 행 삭제가 아닌 상태 되돌리기가 된다 | 첫 포장 때 INSERT해 유니크 제약으로 막기, 검사이력 테이블과 합치기 |
| 2026-10-11 | 고정 파일은 product 테이블의 file\_id 컬럼에 저장한다. 순환 참조를 피하려고 FK는 걸지 않는다 | 포장 시점에 고른 파일을 Worker가 그대로 읽어 압축과 재시도 결과가 바뀌지 않는다. 상태 UPDATE와 같은 문장에서 설정한다 | 압축 시점에 최신 파일 조회, 박스–파일 매핑 테이블(이력 필요 시 도입) |
| 2026-10-11 | 검사 파일 PK는 대리키(file\_id), (시리얼, 검사 시각)에 UNIQUE를 건다 | 재시도로 같은 등록이 와도 한 번만 저장되고, 다른 테이블은 컬럼 하나로 참조한다 | (시리얼, 검사 시각) 복합 PK |
| 2026-10-11 | 제품은 출하돼도 PACKED로 두고, 출하 여부는 packaging 상태로 판단한다 | 출하 한 번에 최대 40만 행을 UPDATE하지 않아 출하 트랜잭션이 짧다 (NFR-2) | 출하 시 모든 시리얼을 SHIPPED로 갱신 |

| 2026-10-11 | MES 업무 정보는 다루지 않는다. 박스·출하 ID는 대리키, 취소는 삭제한다 | 이 프로젝트는 파일 처리에 집중한다. 채번과 취소 이력은 MES가 이미 갖고 있다 | 날짜별 채번 테이블, CANCELLED 상태로 보관 |

## 백로그

해피케이스 이후 하나씩 재현하고 푸는 문제들이다. 각 항목은 이슈로 옮겨 관리한다.

- [ ] 업로드는 됐는데 등록 API가 실패한 파일 (agent 재시도, 등록 API 멱등성)
- [ ] 등록에서 포장 여부를 확인하고 교체하기 전에 포장이 끼어들면, 고정된 파일의 filePath가 바뀔 수 있음 (product 행 비관적 잠금 검토)
- [ ] 같은 등록이 동시에 오면 두 번째 요청이 UNIQUE 위반으로 500이 됨. 처음 들어온 시리얼의 product 생성(serial UNIQUE)도 같음 (트랜잭션 밖 재시도, 409로 agent 재시도, ON CONFLICT 중 선택)
- [ ] 설비 PC마다 시계가 다를 때 최신 파일 판단
- [ ] 겹치는 시리얼을 동시에 포장할 때 데드락 재현·해결
- [ ] 같은 포장·출하 요청이 재시도로 두 번 오면 박스·출하가 중복 생성됨 (멱등 키). 출하 zip의 raw copy와 ZIP64(40만 항목) 동작 검증 (Commons Compress)
- [ ] 압축 실패 시 재시도 정책
- [ ] 서버 장애로 멈춘 Job 감지
- [ ] 출하 압축을 박스 단위로 이어서 하기
- [ ] 파일 단위 진행률과 Job 행 갱신 병목
- [ ] 출하 압축 5분 초과 시 완료 알림 (메일, 푸시)
- [ ] 어떤 박스에도 안 들어간 파일의 삭제 시점
- [ ] 로컬·NAS 저장소 구현체와 presigned URL 대체 방법
- [ ] 시스템 간 인증과 다운로드 권한
