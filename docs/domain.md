# file-archiver 도메인 결정

2026-10-17 · dohyun

지금은 서버 코드를 **file 처리, inspection_file, shipment·packaging·product, 작업 실행**의 네 덩어리로 나눈다. 아래 문제 1~6을 고칠 때 열어야 하는 곳이 가장 적은 구성이다.

## 판단 기준

구조는 문제에서 정한다(문제 → 방법 → 구조). 덩어리를 나눌지는 두 질문으로 판단했다.

1. 그 문제를 고칠 때 열어야 하는 파일(클래스)이 줄어드는가
2. 한 곳만 고치면 끝나는가

한 트랜잭션에서 같이 바뀌는 테이블을 나누면 열 곳과 호출 코드가 늘어난다. 여러 곳에 똑같이 나오는 로직은 한 곳에 모으면 한 번만 고친다.

## 지금 풀 문제

| # | 문제 |
|---|---|
| 1 | 대용량 출하 zip 성능: 파일 100만 건 이상인 출하도 목표 시간(5분, 최대 10분) 안에 zip을 만든다 |
| 2 | zip 실패 후 재처리: 박스·출하 zip 생성이 실패하면 실패 상태를 남기고 다시 처리한다 |
| 3 | 동시 중복 요청: 동시에 들어온 요청 중 일부 파일이나 시리얼이 겹쳐도, 중복 등록이나 이중 포장 없이 한 요청만 반영된다 |
| 4 | 요청 폭주: 처리 용량을 넘는 포장·출하 요청이 몰려도 서버는 죽지 않고, 넘친 요청은 PENDING으로 대기시킨다. 실패한 작업은 최대 3회까지 재처리한다 |
| 5 | 실패 시 진행률 표시: 출하 zip 진행 중 실패하면 실패 상태와 어디까지 처리됐는지(done_units/total_units)를 보여준다 |
| 6 | 작업 중 서버 다운: 포장·출하 zip 처리 중 서버가 죽어도, 재시작 후 멈춘 작업을 찾아 다시 처리한다 |

나중 문제(이번 구조 결정에는 넣지 않음): 서버 이중화 시 storage 관리, storage 이중화, 시스템 인증.

## 덩어리

| 덩어리 | 담는 것 | 이유 |
|---|---|---|
| file 처리 | storage 읽기·쓰기, zip 생성, 업로드 | 1번(zip 성능)은 이 덩어리만 열면 된다. 받은 목록으로만 처리하고 포장·출하를 모른다 |
| inspection_file | 설비의 검사 파일 등록 | 설비 호출 방식이나 파일 등록 정책이 바뀔 때 같이 바뀐다. 포장·출하와 바뀌는 이유가 다르다 |
| shipment·packaging·product | 박스 포장, 출하, 제품 상태 | 포장은 packaging·product를, 출하는 shipment·packaging(가상 포장이면 product까지)을 한 트랜잭션에서 바꾼다. 문제 2·3·4·6에서 이 세 테이블이 같이 나온다 |
| 작업 실행 | PENDING 작업을 집어 가는 Worker, 재처리(최대 3회) | 재처리는 포장·출하에 똑같이 나온다. 재처리·대기 정책이 바뀔 때 이 덩어리만 고친다 |

## 경계에서 정한 것

- **등록 시 product 생성:** inspection_file 쪽이 product 쪽 메서드(예: `registerIfAbsent(serial)`)를 같은 트랜잭션 안에서 호출한다. product 생성 규칙은 product 쪽에 남는다. 이벤트 방식은 inspection_file.product_id의 product FK 때문에 지금은 쓸 수 없다. 등록 트래픽이 커지고 product 생성 조건이 복잡해지면 이벤트 방식으로 바꾸고 그때 FK를 없앤다.
- **zip 생성:** 무엇을 넣을지(종류, 파일 목록)는 shipment·packaging·product가 정해서 넘기고, file 처리는 받은 내용으로 zip을 만들어 올리기만 한다.
- **Worker 위치:** 재처리 로직과 같이 작업 실행 덩어리에 둔다. 포장 기능과 상관없는 기능이다.

## 상태값

packaging과 shipment는 같은 규칙을 쓴다.

| 테이블 | 상태 |
|---|---|
| packaging | PENDING(대기, 시작 전) → PROCESSING(압축 중) → PACKED / FAILED, 출하 후 SHIPPED |
| shipment | PENDING(대기, 시작 전) → PROCESSING(압축 중) → COMPLETED / FAILED |

## 미정

- **진행률 전달 방식:** zip은 file 처리가 만들고 done_units는 shipment에 있다. file 처리가 shipment를 직접 부르면 양방향 의존이 생긴다. 출하 zip 코드를 짤 때 정한다.
